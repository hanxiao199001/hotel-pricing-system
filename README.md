## 🎯 当前进展

### ✅ 已完成

1. **核心架构**
   - 询价工作流抽为唯一实现（`pipeline.py`），CLI 与中台共用
   - 数据库模块（SQLite，幂等写入 + 唯一索引）
   - 定价算法（同档中位价 × 入住率系数）
   - 携程真实采集框架

2. **价格链路（真实数据）**
   - 携程真实采集（子进程调用 Playwright 脚本）
   - 竞品数据校验（状态 / 价格 / 去重 / 城市一致性）
   - 同档中位价定价算法 + 单次幅度上限
   - 市场定位分析（分位数 + 排名）
   - 调价建议生成与落库

3. **决策中台（Web）**
   - 概览 / 价格雷达 / 调价建议 / 系统状态 四页接真实数据
   - 差评预警 / 口碑分析 / 差评回复 三页接真实点评（点一次采集即刷新，1975 条）
   - What-if 试算：拖动入住率、改当前价，实时看建议价怎么变
   - 人工拍板：确认/驳回建议，写入 `price_adjustments`
   - 一键采集：后台线程执行，日志实时回传，单任务互斥

4. **点评 × 定价打通**
   - 房型名归一到档位（12 个原始房型 → 6 个档位 + 床型子维度）
   - 每档位算口碑（均分、差评率、Top 差评主题），判断「撑不撑得住这个价」
   - 结论只作参考，**不并入建议价**——算价口径一行没改
   - 实测结论：档位越高口碑越弱，行政商务房差评率是基础档的 4.1 倍

5. **差评回复草稿**
   - 30 条差评一键出稿，按主题/评分分档语气，覆盖 8 类问题
   - 所有整改动作强制留 `{{整改动作}}` 占位，不编造事实
   - 可选接大模型重写（不配 key 也能用，全走模板）
   - 模型输出若没预留占位符会被拒绝并回退，防止假承诺外发
   - 草稿落库、标记采用/弃用，形成「生成→人工确认→发布」闭环

6. **测试验证**
   - 153 个用例全部通过
   - 真实端到端：海口 48 家竞品，单次采集约 60 秒
   - 数据存储幂等（同一天重复运行不累积）

### 🚧 待完善

1. **入住率自动化** — 目前只能人工每天填写；可考虑从 PMS 导出或房态接口获取
2. **微信通知集成** — `notifier.py` 尚未接入，需要对接真实推送渠道
3. **报表 / 客源 / 协同 / 集团** — 中台已有页面与信息结构，数据仍是静态示例
4. **回复不能自动发布** — 携程回复是写操作，需要商家账号授权；现在只到「复制正文」这一步
5. **各档位没有挂牌价** — 只有起价一个数，所以能判断「撑不撑得住」，算不出「某档该卖多少」
6. **定时任务** — 已内置「每日自动采集」（价格 + 点评各一次，默认 08:00 或当天首次进入触发）；受携程频控限制，不建议更高频

两个入口，共用同一份询价工作流（`pipeline.run_pricing_check`）：

### 1. 中台（浏览器界面，日常用这个）

```bash
cd "D:/TeleAgentWrork/酒店AI/hotel-pricing-system"
python run_webapp.py --open        # 默认 http://127.0.0.1:8765/
```

- 概览 / 价格雷达 / 调价建议 / 系统状态 四页走真实数据
- 其余 6 个模块（差评、口碑、报表、客源、协同、集团驾驶舱）走静态示例数据，页面上有明确标记
- 右上角「立即采集」相当于跑一次 `main.py`，过程日志在右下角实时滚动
- 只监听 127.0.0.1，没有任何鉴权，别直接暴露到公网

### 2. 命令行（跑一次就退出，适合定时任务）

```bash
python main.py
```

### 定时任务（每日自动采集，中台内置）

中台内置「每日自动采集」，默认开启，无需系统级定时器：

- 每天价格、点评各自动采集一次，统一不早于 `DAILY_COLLECT_AT`（默认 `08:00`）：
  - 中台开着没人动 → 到点自动执行；
  - 到点之后当天首次进入中台 → 立即触发（中台 8 点后才启动，启动后约半分钟内补采）。
- 判重记录在 `daily_collects` 表，含手动「立即采集」：当天采过就不再重复，重启中台安全；
  价格类还会核对 `competitor_prices` 里是否已有当天数据（外部跑过 `main.py` 也算已采）。
- `DATA_SOURCE=mock` 时自动跳过，不会把模拟数据写进真实库。
- 自动尝试失败当天不重试（原因见「系统状态」页的每日采集卡片，手动补采即可）——
  频控、登录失效都需要人工判断，盲目重试只会加剧限流。
- 自动采集会打开可见浏览器，依赖 `SCRAPER_PROFILE` 登录态；
  停在登录/滑块页时任务会等人工处理（点评类最多等 `REVIEWS_LOGIN_WAIT` 秒）。
- 开关与参数见 `.env.example` 的「每日自动采集」段。

#### 备选：系统级定时器（不依赖中台进程）

中台没开机的那天不会自动采（开机打卡后补当天一次）。若要电脑一开机就采、
与中台无关，可用系统定时器跑命令行（只采价格；点评采集目前只有中台入口）：

Windows 用任务计划程序：

```bash
schtasks /create /tn "HotelPricing" /sc daily /st 08:00 ^
  /tr "python D:\\TeleAgentWrork\\酒店AI\\hotel-pricing-system\\main.py"
```

Linux 用 crontab：

```bash
0 8 * * * cd /path/to/hotel-pricing-system && python3 main.py >> /var/log/hotel-pricing.log 2>&1
```

> 注意：真实采集受携程频控限制，实测高频运行会被限流（价格变 0）。
> 内置机制与备选方案都是每天一次的低频节奏，符合频控约束；不要改成每小时。

## 🔌 数据来源：模拟 / 真实采集

由 `.env` 的 `DATA_SOURCE` 控制，改完直接 `python main.py` 即可，主程序无需改动。

```bash
DATA_SOURCE=mock   # 默认，内置随机数据，用于开发与测试
DATA_SOURCE=real   # 调用 ctrip_hotel_scraper.py 抓取真实携程数据
```

### 真实模式的前置条件

1. **采集环境**：采集脚本依赖 playwright，跑在独立的 venv 里（`D:\TeleAgentWrork\酒店AI\.venv`，
   Python 3.12），与本项目的解释器分开。路径可用 `SCRAPER_PYTHON` / `CTRIP_SCRAPER_SCRIPT` 覆盖。
2. **浏览器**：本机未安装 Chrome，默认用 Edge（`SCRAPER_CHANNEL=edge`）。
3. **登录态**：携程未登录或访问过频时会**隐藏价格**（实测房型名能抓、价格全为 0）。
   首次使用建议在有头浏览器里手动登录一次携程账号，登录态保存在 `SCRAPER_PROFILE` 指向的目录，
   之后复用。
4. **自家酒店数据**：OTA 搜索把自家酒店当作中心点排除，结果里不含自己，
   所以 `MY_HOTEL_CURRENT_PRICE` / `MY_HOTEL_OCCUPANCY_RATE` 必须人工填写。

### 采集层结构

```
scrapers/
├── runner.py     # 子进程调用采集脚本，处理超时/退出码/临时文件
├── validator.py  # 结果校验：状态、价格、去重、城市一致性
└── adapters.py   # 结果适配：米→千米、评分/点评数转换、酒店ID提取
```

`validator.py` 的**城市一致性校验**是必需的：实测采集脚本在采错城市时依然返回
`status: ok`（请求海口却采回杭州/北京），不做校验会静默污染定价数据。

### 已知限制

- 一次采集约 40–60 秒（不含详情页房型）；开启 `SCRAPER_COLLECT_ROOMS=true` 后
  按酒店数线性增长，47 家约 5–15 分钟。
- 携程有频控：短时间内反复运行会隐藏价格或让列表无法渲染。生产环境建议每天 1–2 次。
- 采集是有头浏览器，不支持无人值守的首次登录；定时任务依赖已保存的 profile 登录态。
- 飞猪脚本同样支持真实采集，但实测有更严格的频控和淘宝登录墙，暂未接入。

### 为什么把工作流抽成 pipeline

原来「采集 → 算价 → 落库」整段写在 `main.py` 里。中台要复用只能 `import main`，
于是命令行和网页端成了两条路径，同一个入住率可能算出两个价。

现在只有一个实现：`main.py` 负责打印和通知，`webapp/api.py` 负责展示和拍板，
算价逻辑一行都没有分叉。`algorithm.py` 的公式、阈值、单次幅度上限全部保持原样。

## 🖥 中台（webapp）

### 数据来源标记

每个接口返回体都带 `source` 字段，页面右上角和卡片上都标出来：

| 标记 | 含义 |
|---|---|
| 实时数据 | 来自 `pricing.db` 或本次实时计算 |
| 历史快照 | 来自真实采集的点评快照，是历史切片，刷新不会更新 |
| 示例数据 | 来自 `webapp/data/static.json`，模块尚未实现 |
| 含示例数据 | 同一页面两者都有（概览页） |

未实现的模块**只做展示，不伪造写操作**——按钮点下去会明确告诉你该模块还没接。

### 口碑两页：接的是真实点评，且可以在页面里重新采集

「差评预警」「口碑分析」两页的数据来自携程点评采集脚本 `ctrip_hotel_reviews.py`
产出的快照，落在 `data/reviews/ctrip_reviews.json`（君华海逸 1975 条公开点评）：

| 页面 | 真实指标 |
|---|---|
| 口碑分析 | 综合评分、好评率、评分档位分布、四维拆解（位置/设施/服务/客房）、分房型口碑、月度趋势、好评提及率 |
| 差评预警 | 差评总数与占比、未回复条数、近 90 天差评、差评主题分布、30 条差评明细、评分最低的一条原文与商家回复 |

计算在 `reviews_analytics.py`（纯函数，可单测），页面组装在 `webapp/review_pages.py`，
采集在 `scrapers/reviews_runner.py`。两个口径要说清楚：

- **差评 = 评分 ≤ 3，好评 = 评分 ≥ 4**，可在 `config.REVIEWS_CONFIG` 改。
- **主题归类是关键词朴素匹配**（`NEGATIVE_THEMES`），不做分词、已做繁简归一化；
  一条点评可命中多个主题，所以主题条数之和大于差评总数。

#### 怎么采集

页面右上角「重新采集点评」，或「系统状态 → 点评采集 → 重新采集点评」，也可以直接调接口：

```bash
curl -X POST http://127.0.0.1:8765/api/reviews/collect
```

采集走的是**携程评论接口翻页**（不是滚动 DOM），完整一轮约 70–90 秒：

```
评论总数=2659（可翻页 1975），pageSize=50，共约 40 页
→ 第 1 页 50 条 … 第 40 页 累计 1975 条
✅ 保留 1975 条，日期 2023-11-11 ~ 2026-11-01
```

三个必须知道的前提：

1. **会打开一个可见的浏览器**。脚本要真实会话参数，无头模式不成立。
2. **依赖已登录的 `SCRAPER_PROFILE`**。停在登录墙/滑块时任务会等人处理，最多等
   `REVIEWS_LOGIN_WAIT` 秒（默认 180）后超时失败。
3. **失败不会破坏旧快照**。结果先写 `*.collecting.json`，校验通过才 `os.replace`
   原子替换；酒店名对不上、评分全为 0、日期越界都会拒绝写入。

另外：连续两次采集时，上一次的浏览器可能还没释放 profile，脚本会在接管 CDP 后秒退。
`reviews_runner` 对这种「25 秒内非零退出」会自动重试一次（实测有效）。

快照文件缺失或损坏时，这两页自动退回 static.json 的示例数据，不会白屏。

### 房型 → 定价：把点评和定价连起来

点评里有房型字段，定价侧只有「起价」一个数，两者原本是断开的。
断点在命名：`豪华客房-大床丨滨海城景`、`豪华客房-双床丨滨海城景`、`雅致豪华房-大床丨滨海城景`
在点评里是三个取值，但对定价来说前两个同档、第三个高一档。不归一化就只能看到 12 个碎片。

`room_reputation.py` 把 12 个原始房型归并成 6 个档位（床型作子维度，不单独定价），
再按档位算均分、差评率、Top 差评主题，最后给一个判断：

| 档位 | 点评 | 均分 | 差评率 | 相对整体 | 判断 |
|---|---|---|---|---|---|
| 豪华客房 | 1,772 | 4.90 | 1.3% | ×0.87 | 口碑支撑强 |
| 雅致豪华房 | 106 | 4.80 | 2.8% | ×1.87 | 口碑中性 |
| 家庭连通房 | 42 | 4.66 | 4.8% | ×3.2 | 溢价承压 |
| 行政商务房 | 38 | 4.74 | 5.3% | ×3.53 | 溢价承压 |
| 套房 | 15 | 4.86 | 0.0% | — | 样本不足 |
| 云杉优眠精选 | 2 | 5.00 | 0.0% | — | 样本不足 |

三条口径值得说明：

1. **用差评率倍数，不用绝对分**。5 分制里 4.90 与 4.85 的差别基本是噪声，
   而差评率 1.3% 与 5.3% 是 4 倍差距，后者才值得动作。
2. **少于 30 条点评的档位不下结论**（`ROOM_PRICING.min_sample`）。
   套房只有 15 条、云杉优眠 2 条，凭十几条点评说「套房口碑好」是不负责的。
3. **起价档位自动推断**：取点评量最大的一档（OTA 最低价房型通常也是点评最多的基础房型），
   可用 `MY_HOTEL_BASE_ROOM_TIER` 覆盖。

结论是反直觉的：**高价档位的口碑反而更弱**。行政商务房差评率是基础档的 4.1 倍，
说明「靠升级房型提价」这条路暂时走不通，应先整改再提价。

页面只陈述「哪些档位明显更弱」，不写「档位越高口碑越弱」——
代码没有验证档位序的单调性，而且六个档位里有三个样本不足。

**为什么只给参考、不改建议价**：建议价必须可复现、可解释、可回溯到每一分钱。
所以这里输出的是「这一档撑不撑得住现在的价」，算价仍由 `algorithm.py` 完成，
一行没改。页面上它出现在两个位置：口碑分析页的独立表格，和概览页调价卡片下方一行。

**目前算不出的**：各档位的实际挂牌价。系统只有起价一个数，所以能判断方向，
算不出「豪华套房该卖多少钱」——那需要从 PMS 导入每档价格。

### 点评归因：规则兜底，模型聚类

差评分析原来是关键词表加一句写死的结论。实测 1975 条快照发现那句话会翻车：
全量口径硬件类 31 次 vs 服务类 11 次（2.82 倍），但切到近 6 个月变成 **2:2 打平**、
第一主题直接是「服务态度」——写死的「短板在硬件而非服务」会和页面上的主题排序自相矛盾。

所以现在分成两层，各管各的。

**第一层：规则（永远在跑，不需要 key）**

`reviews_analytics.attribution()` 按提及数和样本量给五档判定：

| 判定 | 条件 | 页面说什么 |
|---|---|---|
| hardware | 硬件类 ≥ 服务类 ×2，且两侧各 ≥5 次 | 投诉集中在硬件与设施 |
| service | 服务类 ≥ 硬件类 ×2，且两侧各 ≥5 次 | 投诉集中在服务与流程 |
| mixed | 差距不到 2 倍 | 两类相当，不足以归因 |
| insufficient | 任一侧 < 5 次 | 报数字，说明为什么不下结论 |
| none | 没有可归因的差评 | 不做归因 |

关键是**允许不说**。差评全量只有 30 条，切到近 6 个月只剩 4 条，
在 4 条上判断「短板在哪」等于抛硬币——和 `min_sample=30` 是同一个思路。

**第二层：模型（有 key 才跑，失败就退回第一层）**

`reviews_llm.py` 只做关键词表做不到的事：把差评聚成「一次整改动作能解决」的问题。
实测输出（30 条差评 → 4 个问题）：

| 问题 | 严重度 | 归类理由 |
|---|---|---|
| 客房设施老旧 | 高 | 装修、设备、卫浴与霉味反复被提，同一批翻新即可解决 |
| 清洁与布草卫生 | 高 | 洗漱杯、椅子、布草属清洁执行与验收，与硬件翻新不是同一动作 |
| 服务响应与态度 | 高 | 前台态度、反馈无回复、开票推诿指向一线流程 |
| 早餐质量与规则 | 中 | 品种、出品、补费告知方式都属餐饮整改 |

注意它把「老旧」「霉味」合成一个翻新动作，又把「洗漱杯」「布草」拆成清洁执行——
这是关键词表永远做不到的，因为它不知道哪些词指向同一批整改。

四条硬约束：

1. **数字不归模型**。计数、均分、比例先算好再喂，模型不输出任何统计数字。
2. **每条依据必须能对回原文**。引文要在真实点评里找到连续片段，对不上就丢；
   依据全被丢光的问题整条丢弃——光有结论没有出处的判断不许上屏。实测一次调用丢弃 0 条。
3. **结果落盘缓存**。按（快照路径, mtime, size, 模型名, prompt 版本）做 key。
   同一份快照结论固定，不会刷一次页面变一次。二次读取 0.4ms。
4. **失败不阻塞页面**。没 key、超时、JSON 截断、校验不过 → 整块消失，
   页面只剩规则文案，不留空壳、不弹错。

踩过的坑：`max_tokens=1600` 时第四个问题写到一半被截断，JSON 直接解析失败。
现在默认 3000，并加了截断抢救（`_salvage_issues`）——把已经闭合的问题对象
逐个解析出来，抢救不出的半截对象跳过，不做猜测性补全。

严重度衡量的是**整改紧迫性**，不是提及次数，所以会出现「规则说服务侧更轻、
模型却把服务响应标成高」的情况——两个维度不同，页面 note 里有说明。

采集完想立刻生成（不必等页面首次访问，避免那一次同步等待）：

```bash
python -m reviews_llm
```

### 差评回复：生成草稿，但不替你发布

`reply_draft.py` 按差评主题与评分生成中文回复，覆盖 8 类问题（设施/卫生/服务/早餐/
性价比/隔音/泳池/开票），未归类走通用话术。

一条硬规则：**系统不知道酒店实际做了什么整改，所以绝不自己编。**
所有动作句都留 `{{整改动作}}` 占位，页面上给出建议措辞供替换：

> 您提到的设施陈旧问题，确实是我们现在最需要补的短板。我们{{整改动作}}。在您下次入住前会先确认房间设备是否完好。

宁可留一个空让人填，也不写「已全部更换床品」这种听起来漂亮但可能是假的话——
那会变成二次差评的素材。

三个细节：

- **语气按分数分档**：≤2 分用「非常抱歉这次没让您住好」，2–3 分用「抱歉这次没达到您的预期」，
  一上来就「非常抱歉」用在 2.9 分上反而失当。
- **归类误判不会传染到回复**：某条点评原文是「服务真心不错」，却被关键词归类成服务问题。
  统计口径不动（那是 `reviews_analytics` 的事），但草稿会跳过这一项并给出提示，
  不会向客人道歉他刚夸过的东西。
- **一条最多展开两个主题**：超过两个通常是「整体不满意」，逐条罗列反而像模板。

**大模型是可选的增强，不是前置依赖**。没配 `LLM_*` 时全部走模板，功能照常可用。
接了模型也只做一件事：把同一份输入写成更自然的措辞。边界写在 `config.LLM_CONFIG` 的注释里：
只读、不参与算价、可降级。模型输出要过五道校验（长度、必须含占位符、
不得出现「已全部更换」这类确定性措辞、不得推卸责任），任何一道不过就回退模板并说明原因。

草稿可编辑、可保存、可标记「已采用 / 已弃用」，存 `reply_drafts` 表。
但**没有自动发布能力**：携程回复是写操作，需要商家账号授权。现在的闭环止于「复制正文」。

### 人工拍板补上了什么

`price_suggestions.status` 原来永远是 `pending`，`price_adjustments` 表建库起一条记录都没有——
「建议模式」缺的正是确认入口。现在在中台点「确认按此价执行」会：

1. 把建议状态改成 `approved`，记录 `decided_at` / `decision_note`
2. 往 `price_adjustments` 写一条（旧价、新价、理由、执行人、关联建议 id）

**只写本地记录，不会去 OTA 后台改价**。真实改价需要商家后台权限，本系统不碰。

`CTRIP_USERNAME`、`CTRIP_PASSWORD`、`CTRIP_HOTEL_ID` 缺失或为空时，程序会在启动时直接退出，不会带着空凭据去跑爬虫。`NOTIFY_ENABLED` 为 true（未设置时默认 true）时，`NOTIFY_RECIPIENT` 同样必填；不需要通知请设 `NOTIFY_ENABLED=false`。

`.env` 由 `config.py` 按项目根目录的绝对路径加载，与启动目录无关；未安装 `python-dotenv` 时会自动启用内置解析，`python main.py` 在任何解释器下都能读到配置。启动失败时会打印诊断信息（当前解释器、工作目录、`.env` 是否找到及识别到的键名），据此可区分「配置没读到」和「值没填」。

定价策略在 `config.py` 的 `PRICING_STRATEGY` 中调整：

```python
PRICING_STRATEGY = {
    # 入住率分区
    "low_occupancy_threshold": 30,
    "high_occupancy_threshold": 60,

    # 各区间相对「同档中位价」的调整比例
    "low_occupancy_ratio": -0.08,     # 入住率低 → 低于中位价 8% 让价吸客
    "normal_occupancy_ratio": -0.03,  # 正常 → 略低 3%
    "high_occupancy_ratio": 0.06,     # 入住率高 → 高于 6% 吃溢价

    # 同档竞品筛选（以当前价为中心的区间）
    "band_low_ratio": 0.6,
    "band_high_ratio": 1.6,
    "band_min_samples": 3,            # 同档不足则退回全量

    "max_step_ratio": 0.15,           # 单次调价幅度上限
    "floor_ratio": 0.6,               # 相对同档中位价的下限
    "cap_ratio": 1.4,                 # 相对同档中位价的上限
    "min_price": 80,                  # 绝对成本底线
    "max_price": None,                # 不设绝对上限
    "min_change": 5,                  # 变化小于此值不调价
}
```

房型口碑的判断阈值在 `ROOM_PRICING`：

```python
ROOM_PRICING = {
    "min_sample": 30,               # 少于这么多条点评的档位不下结论
    "strong_bad_rate_ratio": 1.0,   # 差评率 ≤ 整体的 1.0 倍 → 口碑支撑强
    "weak_bad_rate_ratio": 2.0,     # 差评率 ≥ 整体的 2.0 倍 → 溢价承压
    "weak_hint_range": [3, 5],      # 溢价承压时建议再让价的百分比
    "base_tier": "",                # 起价档位，留空自动取点评量最大的一档
}
```

### 算法为什么这样设计

旧实现是「竞品均价 ± 固定金额，再夹在 100~180 元之间」。在真实数据下它会失效：
48 家海口竞品均价 ¥242，减去 5 元后仍被 `max_price=180` 压到 180，
导致当前价 ¥367 被建议降到 ¥180（-51%），且三个入住率档位输出完全相同。

现在的逻辑：

1. **用中位数而非均值** —— 一家 ¥697 的五星酒店就能把均值从 220 抬到 242，中位数不受影响。
2. **用比例而非固定金额** —— -10 元对 ¥100 的快捷酒店是 10%，对 ¥600 的酒店只有 1.6%。
3. **只跟同档竞品比** —— 先按当前价 0.6~1.6 倍切出同档，避免拿 ¥63 的客栈和 ¥697 的五星一起平均；同档不足 3 家时退回全量并注明。
4. **单次幅度上限 15%** —— 当前价明显偏离市场时，一步到位容易踩空，分多步靠近。
5. **相对边界替代绝对硬顶** —— 建议价限制在同档中位价的 0.6~1.4 倍内，不再有「所有建议都等于 180」这种硬顶。

调价理由会同时给出**理论目标价**和**本次建议价**，例如：

```
入住率正常(45.0%)，贴近同档中位价保持竞争力；同档21家中位¥268；
理论目标¥260，与当前价相差-29%，超出单次调整上限15%，建议分步靠近
```

## 🐛 已知问题

1. **入住率仍需人工提供**
   - 属于 PMS/商家后台数据，OTA 公开页拿不到
   - `.env` 的 `MY_HOTEL_OCCUPANCY_RATE` 需每天更新，它直接决定建议价的加减方向

2. **采集依赖已登录的浏览器 profile**
   - 未登录携程时列表页只显示「登录以查看会员价」，价格元素是空 div
   - 脚本仍能采到酒店名和房型，但 price 全为 0，校验层会整批拒绝
   - 修复方式：用有头浏览器打开 `SCRAPER_PROFILE` 目录登录一次

3. **微信通知未实现**
   - `main.py` 只把通知内容打印到终端并写文件，未调用 `notifier.py`
   - 中台里点「确认」只写本地调价记录，不会去改 OTA 后台

4. **中台还有 4 个模块只有静态数据**
   - 报表 / 客源 / 协同 / 集团驾驶舱
   - 页面结构和 `block` schema 已定，接真实数据源时前端不用改

5. **点评采集需要可见浏览器，且只覆盖携程**
   - 每日自动采集会以有头浏览器运行点评采集；停在登录/滑块页时最多等 `REVIEWS_LOGIN_WAIT` 秒，需人工处理
   - 依赖已登录的 `SCRAPER_PROFILE`，登录态过期需人工重登
   - 只覆盖携程公开点评，不含美团/飞猪/商家后台
   - 主题归类是关键词匹配（已做繁简归一化），30 条差评里仍有 3 条归到「未归类」

6. **回复草稿不能自动发布**
   - 携程回复是写操作，需要商家账号授权
   - 现在的闭环止于「复制正文」，采用状态靠人工回填
   - 草稿里的整改动作一律留占位符，必须人工确认后才能发

7. **各档位没有挂牌价**
   - 库里只有起价（`my_hotel_prices.price`）一个数，竞品也只有列表页起价
   - 所以房型分析只能判断「撑不撑得住」，算不出「这一档该卖多少钱」
   - 要细化到房型定价，需要从 PMS 导入每档价格，并让采集脚本开 `--collect-rooms`

8. **中台无鉴权**
   - 只监听 127.0.0.1，不要直接暴露到公网
   - 要给外部看，先加反向代理与登录

9. **飞猪暂未接入定时任务**
   - 冷启动需人工扫码登录
   - 同 profile 连跑间隔小于 1 分钟即触发滑块风控
   - 自动滑块逻辑未适配新版 `baxia-punish` 结构

10. **算法与口碑阈值尚未按真实经营数据校准**
   - 定价比例（-8%/-3%/+6%）、单次上限 15%、口碑判定倍数（1.0/2.0）都是通用经验值
   - 建议积累一到两周的实际成交数据后再调
